# هویت، نقش‌ها و دسترسی‌ها

## چرا این بخش مهم است؟

PGClockBot چند لایه هویت و دسترسی دارد. ظاهر یک منو به‌تنهایی تعیین‌کننده مجوز نیست؛ دسترسی واقعی در Web، Bot، Shop و PasarGuard جداگانه کنترل می‌شود.

## هویت Web و Telegram

هویت ادمین Web و ادمین پلتفرم Telegram دو منبع مستقل دارند. وجود یک حساب در Web به‌صورت خودکار آن را به `ADMIN_IDS` ربات تبدیل نمی‌کند و برعکس.

## Owner واقعی

در لایه سازمانی، Owner واقعی یک Principal سطح صفر و فعال است. صرف داشتن برچسب `role=admin` برای دریافت دسترسی Platform کافی نیست.

## Reseller

Reseller یک tenant فروشگاهی مستقل دارد. داده‌های فروشگاه باید با `reseller_id` مربوط به همان فروشگاه محدود شوند. نبودن scope نباید باعث نمایش داده‌های Platform شود.

## pg_staff

`pg_staff` حساب فرعی PasarGuard است که اعتبارنامه اختصاصی خودش را دارد. اگر اعتبارنامه اختصاصی موجود نباشد، مسیر باید fail-closed باشد و نباید از credential مالک اصلی استفاده شود.

## Principal

Principal بخشی از مدل سازمانی جدید است و می‌تواند scope و هویت اختصاصی Web/PasarGuard داشته باشد. سطح Principal و parent آن در تعیین محدوده دسترسی اهمیت دارد.

## Shop Scope

برای Reseller، کاربران، سفارش‌ها، Ticketها و سایر منابع فروشگاهی باید متعلق به همان tenant باشند. `NULL` در مالکیت به معنی «دسترسی جهانی» نیست.

## PasarGuard Scope

مجوزهای PasarGuard از Role واقعی حساب PasarGuard استخراج می‌شوند. منوی مدیریت ادمین‌های PasarGuard Owner-only است و Role محدود نباید با منوی ظاهری مجوز بیشتری دریافت کند.

## Read در برابر Write

دیدن یک منبع همیشه به معنی اجازه تغییر آن نیست. بعضی مسیرها برای مشاهده محدودتر یا متفاوت از Mutation هستند؛ بنابراین هر عملیات باید با Scope و Guard خودش ارزیابی شود.

## مثال

اگر Reseller A سفارشی متعلق به Reseller B را با ID آن سفارش حدس بزند، داشتن ID نباید برای مشاهده یا تغییر کافی باشد. مالکیت منبع باید دوباره بررسی شود.

## اصل امنیتی

هرجا هویت، Scope یا مالکیت نامشخص باشد، رفتار مورد انتظار **رد دسترسی** است، نه fallback به اطلاعات Platform.
